== Точки взаимодействия

Для работы выбраны две основные точки: ввод изменения диспетчером через C-02 и доведение зафиксированных сведений из C-01 через C-03. Первая описана в UI-01, вторая — в контракте IF-01.

. Диспетчер смены (A-01) вводит изменение через рабочее место C-02 и получает сведения о фиксации и доступности пассажиру. Связь: UR-01, BP-01; UML TO-BE, рисунок 5.

. Ядро C-01 передаёт адаптеру C-03 только разрешённые сведения о зафиксированном изменении; адаптер возвращает результат доведения. Связь: FR-01, FR-02, NFR-01; UML TO-BE, рисунок 5.

. Для C-01 и C-03 выбран асинхронный обмен: C-01 передаёт зафиксированное изменение, C-03 отдельно возвращает результат. Синхронный обмен с ожиданием результата здесь неудобен, потому что фиксация и доступность пассажиру происходят не одновременно. Обмен файлами по расписанию не выбран из-за ограничения NFR-01 — 2 минуты в 95 % случаев.

. Пассажир (A-02) получает сведения через согласованный канал, контролируемый предприятием. Конкретный канал в требованиях не выбран; отдельный пассажирский экран не проектируется. Связь: FR-01; UML TO-BE, рисунок 5.

. Справочная служба (D-01), остановочные табло и работа водителей остаются вне границы работ. Отдельный обязательный контракт со справочной не составляется. Связь: C-01 (ограничение), FR-03.

. Согласование руководителя смены A-04 и санкционирование службы движения D-02 учитываются диспетчером до объявления изменения. Прямая программная связь этих участников с C-01 не предусмотрена. Связь: BP-01, D-02; BPMN TO-BE, рисунок 4.

[[IF-01]]
== Контракт IF-01. Доведение изменения

IF-01 «Доведение изменения» — асинхронный обмен между C-01 и C-03. C-01 отправляет сведения после фиксации записи, а C-03 отдельным сообщением возвращает результат.

Связь: FR-01, FR-02, NFR-01; UML TO-BE, рисунок 5.

В графе «Формат» указан тип поля, а в комментарии — его содержание и условия передачи. Конкретный протокол обмена в предыдущих практиках не задан.

|link:requirements.adoc#FR-01[FR-01], link:requirements.adoc#BP-01[BP-01]; BPMN TO-BE, рис. 4.

|[[IF-01.6]]IF-01.6
|При проверке NFR-02: 50 попыток без фиксации должны быть отклонены без смены статуса, 50 попыток с подтверждённой фиксацией должны завершиться успешным доведением; допустимая доля ошибочных успешных доведений — 0 %. Нагрузка — до 20 изменений в час, не более одной активной операции перевода на запись. Результаты и отказы фиксируются в журнале C-01.
|link:requirements.adoc#NFR-02[NFR-02]; UML TO-BE, рис. 5.
|===

Для NFR-01 отсчёт ведётся от фиксации записи в C-01 до доступности сведений в согласованном канале: не более 2 минут в 95 % случаев при нагрузке до 20 изменений в час.

Если изменение зафиксировано заранее, его можно довести как предупреждение о будущем периоде действия.

Асинхронный обмен не меняет этот критерий. Технический протокол и порядок повторных попыток в исходных требованиях не определены.
